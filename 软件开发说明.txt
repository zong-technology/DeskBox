一、项目基本信息

项目名称：DeskBox
AI 助手名称：AI&SI（界面中不再使用 Codex 作为助手名称）
项目类型：Windows 桌面工作台
当前状态：已经完成初步开发，现有程序已打包成 EXE，可以正常运行。
本次目标：在现有项目基础上进行审查、修复、完善和升级，最终交付完整、稳定、可实际使用的新版本 EXE。

核心要求

	1.	不要直接推翻现有项目，也不要在没有分析的情况下重写全部代码。
	2.	先检查现有源代码、项目结构、依赖、配置文件、数据存储方式、构建方式和现有 EXE 的实现情况。
	3.	保留目前已经正常工作的功能和用户数据。涉及数据结构变更时，必须提供兼容或迁移方案。
	4.	优先修复已有功能中的问题，再补齐缺失功能，最后优化界面和性能。

	8.	不得随意更换现有技术栈。确实需要更换时，先说明原因、影响、风险和替代方案。
	9.	不得删除原有项目文件、配置、数据或功能来掩盖问题。
	10.	开始修改前先分析并列出计划；完成后必须测试并提供真实测试结果。

二、产品定位

DeskBox 是一个集成 AI 助手、自动化工作流、天气信息、文件管理、任务提醒、系统监控和工作记录的 Windows 桌面工作台。

它不仅是一个漂亮的桌面启动器，还必须具备真正执行任务的能力。

核心设计原则：

	•	界面简洁、现代、精致。
	•	操作反馈清晰，重要信息一眼可见。
	•	支持自定义 AI 服务商和模型。
	•	支持将多个实际操作串联成自动化工作流。
	•	重要操作可追踪、可取消、可查看日志。
	•	设置、城市、API 配置、任务和历史记录能够可靠保存。
	•	网络异常、API 错误、权限不足、文件不存在等情况必须有合理处理方式。
	•	不允许把尚未实现的功能显示为已完成。

三、整体视觉设计

3.1 风格

采用深色科技风格，整体呈现现代桌面控制中心的感觉。

建议视觉元素：

	•	深色背景、半透明面板、柔和渐变。
	•	适度使用蓝色、青色作为强调色。
	•	卡片边缘简洁，阴影和模糊效果适度。
	•	图标统一，避免混用风格差异过大的图标。
	•	动画流畅、克制，不影响性能。
	•	文字清晰，层级明确，避免过度装饰。

3.2 布局

根据现有项目的技术框架和窗口结构进行优化，不强制推翻现有布局。

建议包含：

	1.	左侧导航栏。
	2.	顶部状态区域。
	3.	中央工作区。
	4.	可配置的功能卡片。
	5.	设置页面。
	6.	通知、错误提示和任务执行状态区域。

建议导航栏目：

	•	首页
	•	AI&SI AI
	•	自动化
	•	文件管理
	•	任务与提醒
	•	天气
	•	系统监控
	•	工作记录
	•	设置

如果现有项目已经有合理的导航结构，应优先保留并完善。

3.3 启动动画

完善现有软件启动画面，不需要展示电脑桌面或模拟用户操作电脑的画面。

启动过程建议：

	1.	显示 DeskBox 标识。
	2.	展示简洁的渐变或粒子动画。
	3.	显示 AI&SI 名称或简短欢迎语。
	4.	显示真实的初始化状态。
	5.	初始化完成后平滑进入主界面。

启动动画要求：

	•	不得阻塞主线程。
	•	不得无故延长启动时间。
	•	加载失败时能够显示具体原因或进入可用的降级状态。
	•	不得将固定延时冒充真实加载进度。
	•	已有成熟启动界面时，在原有基础上优化即可。

四、AI&SI AI 助手

这是项目的核心功能之一，必须优先保证真实可用。

4.1 AI 服务商管理

提供独立的 AI 服务商配置页面。

用户可以：

	•	新增服务商。
	•	编辑服务商。
	•	删除服务商。
	•	设置默认服务商。
	•	设置默认模型。
	•	切换不同服务商。
	•	为不同服务商保存独立配置。
	•	测试 API 连接。
	•	查看连接测试结果。
	•	查看最近一次请求的成功或失败状态。

每个服务商至少支持以下配置：

	•	服务商名称。
	•	API 协议类型。
	•	API Base URL。
	•	API Key。
	•	模型名称。
	•	请求超时时间。
	•	失败重试次数。
	•	是否启用。
	•	是否作为默认服务商。
	•	可选的额外请求参数。

4.2 API 兼容性

尽可能兼容 OpenAI 风格的 Chat Completions 接口及其他已实现的协议。

不能假定所有服务商都使用完全相同的接口。

要求：

	1.	根据服务商协议构造正确请求。
	2.	支持用户自定义 Base URL 和模型名称。
	3.	处理不同服务商的鉴权方式及返回结构。
	4.	对不兼容的接口明确报错，不要假装连接成功。
	5.	API Key 不得硬编码在源代码中。
	6.	不得把 API Key 写入普通运行日志。
	7.	不得将 API Key 上传到与请求无关的服务器。
	8.	如果技术框架支持，应使用系统凭据存储或安全的本地密钥存储机制。
	9.	若只能使用本地配置文件保存密钥，必须明确说明风险，并采取适当保护措施。
	10.	用户删除服务商后，应按明确的数据保留规则处理其配置和密钥。

4.3 连接测试

点击“测试连接”后，必须实际发送请求或执行能够验证接口有效性的请求。

测试结果应区分：

	•	连接成功。
	•	API Key 无效。
	•	模型不存在。
	•	Base URL 错误。
	•	网络连接失败。
	•	请求超时。
	•	服务商限流。
	•	服务端错误。
	•	接口协议不兼容。
	•	其他未知错误。

显示错误摘要，并在必要时提供详细信息。

不能仅凭 Base URL 格式正确就显示连接成功。

4.4 AI 对话

实现以下功能：

	•	新建对话。
	•	删除对话。
	•	切换历史对话。
	•	自动保存对话。
	•	显示用户消息和 AI 回复。
	•	支持多轮上下文。
	•	支持流式输出，前提是所用接口及现有技术栈支持。
	•	支持停止正在进行的请求。
	•	支持重新生成回答。
	•	支持复制消息。
	•	显示当前服务商和模型。
	•	支持在对话过程中切换模型。
	•	显示请求失败原因。
	•	支持合理的超时和重试策略。

AI 返回内容应正确处理 Markdown、代码块和普通文本。

如果请求失败，必须保留用户已经输入的内容，不能无故清空对话。

4.5 AI 的真实执行能力

AI&SI 不应仅限于聊天。

应通过受控的工具调用机制，让 AI 在用户授权后执行可用任务，例如：

	•	搜索指定目录中的文件。
	•	读取用户指定的文档。
	•	总结文档。
	•	根据用户要求创建任务。
	•	将内容保存为文件。
	•	整理指定文件夹。
	•	生成工作报告。
	•	触发已经配置的自动化工作流。
	•	查询 DeskBox 内部可访问的任务状态和运行记录。

执行规则：

	1.	AI 先理解用户意图，再选择已注册且允许使用的工具。
	2.	不允许 AI 直接执行任意系统命令或不受限制的代码。
	3.	文件操作必须限制在用户授权的范围内。
	4.	删除、覆盖、批量移动等高风险操作，执行前必须明确确认。
	5.	不得把 API 返回的文本直接当作可执行命令。
	6.	工具执行失败时，向用户说明具体原因。
	7.	记录任务名称、开始时间、结束时间、执行结果和错误信息。
	8.	允许用户中止正在执行的任务。

如果当前版本尚未具备工具调用能力，应基于现有架构逐步实现，而不是只添加聊天界面的按钮。

五、自动化工作流引擎

自动化是 DeskBox 的另一项核心功能。

必须建立真正运行的工作流执行引擎，而不是只提供工作流编辑器。

5.1 工作流管理

支持：

	•	新建工作流。
	•	编辑工作流。
	•	删除工作流。
	•	复制工作流。
	•	启用或禁用工作流。
	•	手动运行。
	•	查看执行记录。
	•	查看最近一次执行结果。
	•	取消正在运行的工作流。
	•	设置工作流名称和说明。

5.2 工作流节点

根据现有架构逐步实现以下节点：

触发节点

	•	手动触发。
	•	按计划触发。
	•	文件变化触发（平台支持时）。
	•	指定事件触发。

条件节点

	•	文本条件。
	•	文件是否存在。
	•	任务状态判断。
	•	执行结果判断。
	•	简单逻辑判断。

AI 节点

	•	文本总结。
	•	文本分类。
	•	文本提取。
	•	内容生成。
	•	根据上下文判断下一步操作。

AI 节点必须使用用户当前配置的真实 AI 服务商和模型。

操作节点

	•	读取文件。
	•	搜索文件。
	•	创建文件。
	•	复制文件。
	•	重命名文件。
	•	保存 AI 处理结果。
	•	创建任务。
	•	生成报告。
	•	发送应用内通知。
	•	调用其他已注册的工作流。

5.3 执行引擎要求

	•	节点按配置顺序执行。
	•	节点之间能够传递数据。
	•	上一个节点的输出可以作为下一个节点的输入。
	•	节点失败时能够停止、跳过或按配置处理。
	•	具备超时控制。
	•	支持有限次数的失败重试。
	•	支持取消执行。
	•	记录每个节点的输入摘要、输出摘要、耗时和结果。
	•	不得将尚未执行的节点显示为成功。
	•	对可能造成数据损失的操作，执行前必须确认。
	•	避免无限循环和无限重试。
	•	对并发任务设置合理限制。

5.4 自动化示例

示例一：文档总结

	1.	用户选择文件。
	2.	系统读取文件。
	3.	AI 总结文件内容。
	4.	将摘要保存到指定位置。
	5.	生成执行记录。
	6.	向用户显示结果文件位置。

示例二：文件整理

	1.	用户选择需要整理的目录。
	2.	系统扫描文件并生成清单。
	3.	AI 根据用户要求提出分类建议。
	4.	用户确认整理方案。
	5.	系统执行复制、移动或重命名。
	6.	生成操作记录。

示例三：定时工作报告

	1.	到达设定时间。
	2.	收集用户授权的任务或工作记录。
	3.	AI 生成报告。
	4.	保存报告。
	5.	在 DeskBox 内通知用户。

注意：如果当前项目还没有完整的调度机制，应先实现可靠的本地调度功能，并明确软件退出后任务是否继续运行。不得宣称程序关闭后仍会执行，除非确实实现了后台服务或其他可靠机制。

六、天气模块

天气功能必须使用真实天气数据源。

不能只修改城市名称而继续显示旧城市的天气数据。

6.1 城市管理

支持：

	•	搜索城市。
	•	从搜索结果中选择城市。
	•	添加常用城市。
	•	切换当前城市。
	•	删除常用城市。
	•	保存默认城市。
	•	在多个城市之间切换。
	•	显示城市名称和必要的地区信息，避免同名城市混淆。

城市选择应尽可能使用城市唯一标识或经纬度，不应只依靠字符串匹配。

6.2 天气数据

在选用的数据源能够提供的前提下，显示：

	•	当前天气。
	•	当前温度。
	•	体感温度。
	•	天气描述。
	•	最高温和最低温。
	•	湿度。
	•	风速。
	•	降水概率。
	•	未来数小时天气。
	•	未来数天天气。

不同天气 API 提供的数据可能不同，应根据实际接口能力决定显示内容。

6.3 天气 API

	1.	优先使用可靠、合法、具有清晰使用条款的天气 API。
	2.	需要 API Key 的服务，应提供可配置方式。
	3.	记录真实的数据更新时间。
	4.	支持手动刷新和合理的自动刷新。
	5.	使用适当缓存，避免频繁请求。
	6.	处理网络中断、限流、授权失败和数据格式错误。
	7.	请求失败时可以展示缓存数据，但必须标记数据可能已过期。
	8.	不得把虚构天气数据作为真实数据展示。
	9.	不得把固定的城市天气写死在代码中冒充实时天气。

6.4 城市切换验收要求

当用户从城市 A 切换到城市 B 时，必须正确更新：

	•	城市名称。
	•	当前温度。
	•	天气图标。
	•	天气描述。
	•	最高温和最低温。
	•	湿度、风速等其他已显示指标。
	•	逐小时预报。
	•	多日预报。
	•	数据更新时间。

切换城市后，必须确认请求参数或城市标识已经改变，并确保界面展示的是城市 B 对应的数据。

如果新请求失败，应明确提示，并按合理策略保留上次有效数据，不得静默显示错误城市的数据。

七、文件管理模块

提供真实的本地文件管理功能。

建议支持：

	•	选择目录。
	•	浏览目录。
	•	搜索文件。
	•	按文件名、类型、修改时间等筛选。
	•	查看文件大小和修改时间。
	•	查看文件基本信息。
	•	复制文件。
	•	重命名文件。
	•	创建文件夹。
	•	移动文件。
	•	读取支持格式的文档。
	•	将 AI 生成的内容保存为文件。

安全要求：

	1.	不得未经授权扫描整个磁盘。
	2.	文件操作应限制在用户明确选择或授权的目录内。
	3.	批量操作应提供操作预览。
	4.	覆盖或删除文件前必须进行确认。
	5.	文件操作失败时显示原因。
	6.	记录重要文件操作。
	7.	不得未经允许上传文件到外部 AI 服务。
	8.	当 AI 需要读取文件并将内容发送给外部服务时，应明确告知用户并遵循授权设置。
	9.	不支持读取的文件格式应明确提示，而不是显示乱码后假装成功。

八、任务与提醒模块

实现基本的任务管理功能：

	•	创建任务。
	•	编辑任务。
	•	删除任务。
	•	标记完成。
	•	设置优先级。
	•	设置截止时间。
	•	设置提醒时间。
	•	查看待办任务。
	•	查看已完成任务。
	•	按状态筛选。
	•	按时间排序。
	•	保存任务数据。
	•	提供应用内提醒。

如果系统通知不可用，应提供应用内提醒或明确的降级提示。

任务数据不得因为应用升级、窗口关闭或普通重启而丢失。

九、系统监控模块

在操作系统及现有技术框架允许的范围内，展示真实的系统状态：

	•	CPU 使用率。
	•	内存使用情况。
	•	磁盘空间。
	•	网络状态。
	•	应用自身运行状态。

要求：

	•	数据必须来自真实系统指标。
	•	定时刷新不能造成明显卡顿。
	•	对不支持的指标明确提示。
	•	不得为了展示动画而生成虚假的系统数值。
	•	避免过高频率的轮询。
	•	系统监控采集失败时不能伪装成正常数据。

未经用户明确授权，不进行不必要的进程监控、敏感数据收集或后台数据上传。

十、工作记录与执行日志

建立统一的工作记录模块。

记录范围包括：

	•	AI 请求状态。
	•	自动化执行情况。
	•	文件操作。
	•	任务创建与完成。
	•	配置修改的重要事件。
	•	错误与异常。
	•	程序启动和关闭的重要状态。

每条记录尽可能包含：

	•	时间。
	•	事件类型。
	•	事件名称。
	•	执行结果。
	•	耗时。
	•	错误摘要。
	•	相关任务标识。

要求：

	1.	提供搜索和筛选。
	2.	支持查看详情。
	3.	支持清理历史记录。
	4.	可以限制日志保留时间或数量。
	5.	不得记录 API Key、密码等敏感凭据。
	6.	不得把完整敏感文档内容默认写入日志。
	7.	关键错误需要足够的信息供开发者排查。

十一、设置中心

建立统一设置中心，并与真实程序配置关联。

建议包含以下页面：

外观设置

	•	深色或浅色主题。
	•	强调色。
	•	窗口行为。
	•	动画开关。
	•	字体和界面缩放（现有框架支持时）。

AI 设置

	•	服务商管理。
	•	默认服务商。
	•	默认模型。
	•	API 参数。
	•	超时和重试策略。
	•	对话历史管理。

天气设置

	•	默认城市。
	•	常用城市。
	•	数据源配置。

十六、开发执行流程

第一阶段：项目审查

	8.	当前 EXE 的构建方式。
	9.	主要稳定性问题。
	10.	推荐的升级顺序。

在完成审查之前，不要贸然大规模改写代码。

第二阶段：制定修改计划

将工作分为：

	•	P0：启动、崩溃、数据安全、核心功能故障。
	•	P1：AI API 配置和对话、天气真实数据、自动化执行引擎。
	•	P2：文件管理、任务提醒、日志、备份。
	•	P3：界面优化、动画、其他体验改进。

根据现有代码的实际情况调整优先级，并说明原因。

第三阶段：逐步实施

每完成一个模块：

	1.	修改代码。
	2.	检查依赖。
	3.	运行相关测试。
	4.	修复发现的问题。
	5.	更新功能状态。
	6.	检查对其他模块的影响。

不要一次性生成大量未经验证的代码，也不要用空函数、固定数据或临时假实现代替真正功能。

第四阶段：整体测试

完成模块后进行整合测试，重点验证：

	•	模块之间的数据传递。
	•	API 配置与 AI 对话的关联。
	•	AI 工具调用与自动化引擎的关联。
	•	天气城市选择与真实请求的关联。
	•	设置和本地数据持久化。
	•	程序异常退出后的恢复能力。
	•	关闭窗口和取消任务的行为。

第五阶段：重新打包

在源代码修改和测试完成后，重新构建发布版本。

验证新 EXE 能够正常启动，确认配置读取、文件资源、数据库和核心功能没有因为打包而失效。

第六阶段：交付报告

最终报告必须包含：

	•	已完成的功能。
	•	修改的主要文件。
	•	修复的问题。
	•	实际执行过的测试。
	•	测试通过与失败的数量。
	•	未完成的功能。
	•	仍存在的风险。
	•	新版 EXE 的实际位置。
	•	如何运行和升级。
	•	如何备份和恢复用户数据。

所有结果必须以真实执行和验证为依据。
